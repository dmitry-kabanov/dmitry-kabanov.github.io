DONE Using Docker Sandboxes with Google Antigravity

It is 2026, and it is common to run AI agents in a terminal or an integrated development environment for coding tasks.

The problem is, AI agents can be insecure to run directly on your machine: only in Summer 2026 were several incidents reported.1 I have recently experienced a strange situation myself when Antigravity, an AI agent from Google, has asked me if it was allowed to run tests from the Tests/ directory one level above the current working directory, because it has looked there for unknown reason. Of course, many software packages look for different things on the file system, for example, for a C compiler, etc. However, they usually check some predefined system locations like /usr/bin on Linux.

So, after that had happened, I have started to think about running AI agents strictly in virtual machines instead of directly. It turned out that Docker Inc. has a special solution for this: Docker Sandboxes. These are isolated virtual machines that also run Docker containers inside of them. That is, each sandbox has its own Docker daemon, filesystem and network, so it cannot break into other Docker containers (normally, Docker containers share the same kernel, for example, on macOS several Docker containers run inside the same virtual Linux machine). Hence, the sandboxes are designed to be more secure: however, they use normal Docker facilities to automatically mount a project directory inside the sandbox, so that an AI agent can work with the project code.

Docker Sandboxes can be used with different AI agents. Below I describe how to use them with Google Antigravity.

How to run Google Antigravity

First, install the sbx utility as instructed on that page.

Many popular AI agents are supported and can be started with the command

sbx run <agent>

where <agent> is the lowercase name of an AI agent.

Strangely, sbx run gemini still exists, although gemini is deprecated since June 2026; however, sbx run antigravity is not yet available.2

Fortunately, there is an official Docker image for Google Antigravity. It can be run with the command:

sbx run "docker.io/sbx/antigravity:latest"

When the container starts, one needs to authorize the agent, which opens an authorization webpage in a browser. After that, using the agent inside the sandbox is as convenient as running it directly on the machine, because the project directory is automatically mounted inside the sandbox. Yet, running inside the sandbox should be more secure, as there is more control over what the agent can access on your computer.

TODO Use git submodule for dependency

This is workflow when you have two projects tracked in Git, and one of the projects is a dependency for another one. Important part of this particular workflow is that we want to track the dependency continuously: not by a specific commit but by a branch.

Let’s call the dependency project simply a dependency, and the other project a root project.

Git has a solution for version-tracking dependencies using Git submodules.

We add the dependency project as a Git submodule for the root project and point it to the main branch of the dependency:

git submodule add -b main <dep-URL> <dep-path>

where <dep-URL> is the remote URL of the dependency, and the <dep-path> is where it inside the root project it should be checked out. Note that if the dependency repo is already in that path, Git will notice it and will just say “Adding existing repo at ‘<dep-path>’ to the index”. Otherwise, it will clone the dependency repository to that path. Note also that the syntax of git submodule add is basically like the syntax of git clone: if you do not provide <dep-path>, it will use the repository name as <dep-path>.

Now, if you do git status, you will see that the file .gitmodules will be added with the information given in the command submodule add above. Besides that, it will be reported that a new file, which is actually the path where the dependency is checked out is staged to be committed. Git actually tracks the whole directory of the submodule as a file with a given commit hash.

Note that the work with the dependency repo should be done still in the directory of the dependency. Whenever there will be new changes there, git status in the root repo will report that there are changes, which can be staged for commit with git add <path>.

Workflow improvement. When you commit changes in the submodule repo, and update the superproject repo, and then you push the superproject repo, it can happen that the submodule repo was not pushed. Hence, other developers or CI server will not be able to checkout the required version of the submodule repo.

Git provides a special configuration setting that will reject to push the superproject repo, if the required changes of the supermodule repo are not on the remote.

One way to set this option is

git config push.recurseSubmodules check

then an attempt to push the superrepo will show an error message:

The following submodule paths contain changes that can
not be found on any remote:
  <submodule-path>

Please try

        git push --recurse-submodules=on-demand

or cd to the path and use

        git push

to push them to a remote.

fatal: Aborting.

and this error message gives a hint that we can config git to automatically push the submodules when needed:

git config push.recurseSubmodules on-demand

However, I would not recommend to use this option, especially in cases when the superproject repo and the submodule repo are on branches with different names. It is easier to simply switch to the submodule repo and do git push origin there, and then to do the push in the superproject.

There another thing. We can modify the submodule worktree and forget to commit it. Then in the superproject repo, git status says that the submodule has new changes.

However, if you do git add <submodule-path>, it will silently do nothing: git sees that the submodule has exactly the same HEAD hash as before, hence, it does nothing. It does not know that we forgot to commit the changes.

To prevent such a situation, it is handy to add the following pre-commit Git hook (do not confuse with the Python utility pre-commit that does the similar thing):

# Check for uncommited changes in the submodule in the <submodule-path>.
dirty_themes=$(git status --porcelain | grep '^.M <submodule-path>/')
if [ -n "$dirty_themes" ]; then
    echo "ERROR: There are uncommitted changes in the /themes subdirectory:" >&2
    echo "$dirty_themes" >&2
    echo ""
    echo "Switch to the corresponding submodule repo and commit the changes there." >&2
    exit 1
fi

Now we have two protections:

  • Forgetting to commit changes in the submodule before commiting in the superproject
  • Forgetting to push changes in the submodule before pushing in the superproject
